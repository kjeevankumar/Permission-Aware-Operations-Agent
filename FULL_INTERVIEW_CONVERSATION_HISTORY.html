    2. Explanation of Major Folders & Separation of Responsibilities



  • app/api/ (Presentation Layer): Exposes RESTful endpoints (/auth, /confirmations, /chat). Handles request routing and parameter parsing. Business logic and raw queries are strictly prohibited here.
  • app/core/ (Core Primitives): Houses cross-cutting concerns: bcrypt hashing, JWT issuance and decoding, dependency injection factories, and the domain exception hierarchy.
  • app/database/ (Data Persistence & Models): Contains SQLAlchemy 2.0 declarative models, connection engines, and the seed script. Every model uses explicit typing (Mapped[], mapped_column()) and appropriate types (sa.Uuid, sa.Numeric(10, 2) for currency, sa.DateTime(timezone=True)).
  • app/schemas/ (Data Transfer Objects): Pydantic v2 schemas defining input validation and sanitized output structures (passwords and internal secrets are never exposed).
  • app/security/ (Defense & RBAC Engine): Core policy enforcement layer: - authentication.py: Resolves UserContext directly from the database; never trusts client-provided tenant headers or roles. - permissions.py: Evaluates effective permissions by combining role permissions, numeric constraints, and user-level overrides. - constraints.py: Enforces operational boundaries (max_rows, max_discount_pct, own_records). - tenant.py: Injects tenant filters (WHERE hospital_id = :id) into queries.
  • app/agent/ (AI Agent Foundation): Prepares clean structural contracts (BaseLLMClient, IntentParser, ParsedOperationIntent, SYSTEM_SECURITY_PROMPT) for Phase 2 without placeholder mocks or fake checks.
  • app/operations/ (Domain Queries): Reusable query operations for inventory, billing, and user access that enforce tenant boundaries.
  • app/services/ (Orchestration & State Mutation): Coordinates multi-step business logic: - preview.py: Dry-run execution that computes before/after state diffs and checks policy limits. - confirmation.py: Manages TTL lifecycle and triggers execution. - execution.py: Atomically applies approved modifications within a single database transaction. - audit.py: Records immutable audit logs for every state change.
  • tests/ (Verification Suite): Comprehensive tests covering database integrity, JWT authentication, tenant isolation barriers, and constraint enforcement.

    3. Database Design & Entity Relationships



    The schema is normalized, enforces referential integrity via foreign keys, and indexes hospital_id across all business tables.

    11 Database Tables Implemented

    1. hospitals: Root tenant model (id, name, code, city, state, is_active, timestamps). 2. users: Hospital staff accounts (id, hospital_id [FK], username, email, full_name, hashed_password, is_active, timestamps). 3. roles: Global standard roles (id, name [Admin, Billing Manager, Pharmacist, Front Desk, Doctor], description). 4. permissions: Discrete permission actions (id, code, description, category). 5. role_permissions: Role-to-permission mapping with role-specific constraints stored as JSON (role_id [FK], permission_id [FK], constraints [JSON]). 6. user_roles: Tenant-isolated user-to-role association (hospital_id [FK], user_id [FK], role_id [FK]). 7. user_permission_overrides: User-specific access grants or revocations (hospital_id [FK], user_id [FK], permission_id [FK], is_granted [bool], constraints_override [JSON], reason). 8. inventory_items: Pharmacy and medical stock (id, hospital_id [FK], sku, name, category, batch_number, quantity, reorder_level, unit_price, expiry_date, location, timestamps). 9. bills: Patient billing invoices (id, hospital_id [FK], bill_number, patient_name, patient_mrn, total_amount, discount_pct, final_amount, status, doctor_id [FK], created_by_user_id [FK], bill_date, timestamps). 10. pending_operations: Staged operations awaiting confirmation (id, hospital_id [FK], user_id [FK], operation_type, target_resource, filter_criteria [JSON], proposed_changes [JSON], impacted_row_count, preview_diff [JSON], status, expires_at, confirmed_at, confirmed_by_user_id). 11. audit_log: Immutable audit records (id, hospital_id [FK], user_id [FK], action, resource_type, resource_id, status, before_state [JSON], after_state [JSON], metadata_info [JSON], ip_address, created_at).

    Critical Architectural Constraints Enforced

  • Multi-Tenant Boundary: Every business table contains hospital_id with non-nullable constraints and foreign keys to hospitals.id.
  • Single Hospital Belonging: Every user belongs to exactly one hospital tenant via User.hospital_id.
  • Zero Financial Deletions: There is no bills.delete permission anywhere in the system; invoices cannot be deleted, only transitioned through statuses (draft, pending, paid, cancelled, disputed).
  • Separation of Permissions and Constraints: Permissions represent *capabilities* (e.g. bills.discount); constraints represent *dynamic limits* (e.g. {"max_discount_pct": 10}).
